# Architecture

How the harness is built and why: what gets installed where, how the plan is
modelled, and which rules are enforced by which layer. For the step-by-step
cycle, see [usage](usage.md); for the knobs, see [configuration](configuration.md).

## Separation of powers

Two engines, each with the work the other must not do:

| Engine | Writes | Never writes |
|--------|--------|--------------|
| **Claude** (leader + claude-planner + implementer) | the plan (`docs/plan/`, claude-planner only), `src/`, `tests/unit/`, `progress/current.md`, `progress/impl_<N.M.K>.md` | `tests/acceptance/`, Codex verdicts and seals, commits |
| **Codex** (codex-planner + reviewer + documenter) | gate verdicts, acceptance tests, `docs/reference/`, `progress/history.md`, the close commit message | production code, unit tests, `.git` |

Whoever writes the code is not the one who approves, documents or commits it.
The hooks and `make check` enforce this split; it does not depend on the model
following instructions.

## Distribution model

The toolkit is cloned once per machine (`~/.claude-codex-harness`). `install.sh`
installs it onto a project in a **hybrid** way:

| Mechanism | What | Why |
|-----------|------|-----|
| **Symlink** | `agents/`, `codex/`, `skills/`, `settings.json` → `.claude/`; `lib/` → `harness/` | `git pull` in the toolkit updates every installed project at once |
| **Copy**    | `CLAUDE.md`, `AGENTS.md`, `Makefile`, `CHECKPOINTS.md`, `docs/`, `progress/` | each project customizes them; never overwritten without `--force` |
| **Generated** | `feature_list.json` | derived from `docs/plan/` by `make plan`; never copied or hand-edited |

Because `harness/` is a symlink, a fix to `lib/` reaches installed projects
immediately. Copied templates (for example `progress/history.md`) do not: a
project keeps the version it was installed with. That is why what every
project must share lives in `lib/` and the copies only point to it:

| Shared file (`lib/`, reached as `harness/`) | Pointed to by the copied file |
|---|---|
| `harness.mk`: the harness Make targets (`plan`, `status`, `check`, `issue`, `issue-start`, `issue-new`) | `Makefile`: its own toolchain targets + `include harness/harness.mk` at the end |
| `WORKFLOW.md`: leader role, rules, startup protocol, issues lane | `CLAUDE.md`: `@harness/WORKFLOW.md` + project context; `AGENTS.md`: a pointer |
| `pr_template.md`, `issue_template.md` | (used by the harness scripts directly) |

Copied files change only through `install.sh <project> --migrate`
(`lib/_upgrade.py`, see [usage](usage.md)): dry-run by default, `--apply` writes
all-or-nothing with backups in `.harness/migrations/` and `--rollback`; links are
verified, never written. `templates/MANIFEST.toml` (`lib/_templates.py`) versions
each managed file (whole file, or only its harness fragment) with every released
version kept in `templates/_bases/`; the project's `.harness/templates.json`
records what it has and its migration level.

### Machine-level config (`link-global.sh`)

Skills and the global `CLAUDE.md` are team-wide, so the toolkit holds the real
content and each machine symlinks `~/.claude` into it:

| Toolkit (real, versioned) | `~/.claude` (symlink) |
|---------------------------|-----------------------|
| `skills/`                 | `~/.claude/skills`    |
| `global/CLAUDE.md`        | `~/.claude/CLAUDE.md` |

`install.sh` runs `link-global.sh --quiet` at the end; it is idempotent. It
backs up an existing real file before linking and preserves machine-local
extras written into `skills/` by the tooling (`.atl/`, `.claude/`, and
`synced/`, the account skills Claude Code caches there). All three are listed
in `skills/.gitignore`. Editing a skill edits the toolkit, so `commit` + `push`
shares it with the team.

## Planning model

The leader talks to the user and runs every gate, the `claude-planner` subagent
(Opus 5.5 / xhigh) writes the plan from the leader's brief, Codex reviews it at
every level, and the human approves each level before the next one starts. `docs/plan/` is the single
source of truth:

```
docs/plan/
  PLAN.md                               vision, goals, scope, architecture + generated index
  phase-NN-<slug>.md                    one per phase: title, goal, its tasks N.M
  phase-NN-<slug>/<N.M.K>-<slug>.md     one spec per subtask: status, layer, depends,
                                        files (1-3, or none if test-only), acceptance, description
```

- **Every phase is planned up front** (title + goal), so the whole scope is
  visible. **Tasks and subtasks are planned one phase at a time**: phase N+1 is
  broken down only once phase N is done.
- **Status is written only in the subtask specs.** Task and phase status,
  `feature_list.json` and the index inside `PLAN.md` are generated by `make plan`.
- The **unit of work is the subtask `N.M.K`**. Its id is used everywhere:
  `progress/*_<N.M.K>.md`, `tests/acceptance/test_<N.M.K>.py`,
  `docs/reference/<N.M.K>-<slug>.md` and the commit footer
  `Plan: docs/plan/phase-NN-<slug>/<N.M.K>-<slug>.md`.

## Flow

```
[leader] stack step, one question at a time: project type + language first, then
   only the categories that apply (reads the code and its manifest first)
   → [claude-planner] docs/stack.md (each decision and why)
   → [Codex] stack gate → STACK_APPROVED (sealed) → you approve
[leader] discovery on docs/stack.md, one question at a time (reads the repo first if there is code)
   → [claude-planner] PLAN.md + every phase file (title + goal)
   → [Codex] roadmap gate → ROADMAP_APPROVED (sealed) → you approve
[claude-planner] break down the current phase: tasks only
   → [Codex] phase gate → PHASE_APPROVED (sealed) → you approve
per task N.M (in order):
   → [leader] kickoff: review the previous task, one question at a time if needed,
   → [claude-planner] one spec per subtask of this task
   → [Codex]  task gate → TASK_APPROVED (sealed) → you approve
per subtask N.M.K (in order, respecting depends):
   → [leader]      task branch + status in_progress + make plan
   → [Codex]       plan gate: review the spec + write tests/acceptance/test_N.M.K.* → PLAN_APPROVED (sealed)
   → [implementer] inner TDD (unit + code) → make verify green
   → [Codex]       code gate → APPROVED
   → [Codex]       close: docs/reference/<N.M.K>-<slug>.md + status: done + make plan
                   + progress/ + ONE commit  (type(scope): what [N.M.K], Plan: footer)
   → make status → you approve the next subtask
task done → [Codex] task-close gate: traceability matrix → TASK_CLOSE_APPROVED (any gap blocks)
phase done → [Codex] phase-close gate (against PLAN.md) → PHASE_CLOSE_APPROVED
   → break down the next phase …
(details and cost: docs/design/task-flow.md)
```

## Issues lane

A GitHub issue (a bug, a refactor, a small enhancement) can appear at any point
and often touches a phase that is already done. It is planned **apart from the
phases and tasks**, with the same process, roles and gates; the full design,
reviewed by Codex, is [design/issues-lane.md](design/issues-lane.md).

```
docs/plan/issues/
  ISS-<n>-<slug>.md                   issue header: link, type, origin, priority, goal,
                                      the imported issue body in its own section
  ISS-<n>-<slug>/ISS-<n>.<k>-<slug>.md   one spec per issue subtask (same format as N.M.K,
                                      plus an optional `migrates:` list)
```

- **Queue and claim on GitHub**, so every machine and teammate sees the same:
  labels `priority:now|next|backlog` (`make issue N=<n>`), then `make issue-start
  N=<n>` claims it (assignee, `status:in-progress`, and an exclusive annotated
  tag `claim/ISS-<n>` pushed without force) and creates the branch
  `<type>/ISS-<n>-<slug>` from `origin/main`. The type comes only from the label.
- **Timing**: `next` waits until the task in progress is merged into `main`;
  `now` interrupts a task between subtasks and `harness/issue.sh resume` returns
  to it once the issue is merged; `backlog` waits for the user.
- **Rules**: issues never count in phase progression; an issue subtask starts
  once its issue is `ISSUE_APPROVED` (the issue gate, sealed) and its depends are
  done; one `in_progress` leaf across both lanes; the issue branch is enforced.
- **Sealed oracles of other subtasks** change only through `migrates:`: frozen
  at the issue gate, checked before the plan gate (`migrates-ready`), re-sealed
  atomically at `PLAN_APPROVED` (`lib/_migrate.py`).
- **Close**: one commit per `ISS-<n>.<k>`; the last one opens one PR with
  `Closes #<n>`; the claim is dropped once the PR is open.
- **New issues**: a draft reviewed by Codex (`DRAFT_APPROVED`, sealed) is
  published only with the user's OK, byte for byte.
- Network (`gh`) only in explicit commands and `make status`'s queue block;
  `make check` and the hooks never use it.

## Harness rules

Enforced by the hooks in `settings.json` and by `make check`:

0. **Stack before the plan** (issue #115). While `docs/stack.md` is not
   `STACK_APPROVED` with its seal (`progress/stack.sha256`) matching, the roadmap
   gate refuses to run and `make check` fails once a phase file exists; any
   change to `docs/stack.md` voids the approval (stack gate again). Projects
   whose roadmap or plan (a phase) was approved before the stack step only get a
   WARN, with or without `docs/stack.md`. Dependency drift between `pyproject.toml`
   `[project] dependencies` and `docs/stack.md` is a WARN (`lib/_stack.py`).
   **Plan gates.** No phase is broken down without `progress/roadmap_review.md` =
   `ROADMAP_APPROVED`; phases are broken down one at a time; no subtask starts
   without `progress/phase_review_<NN>.md` = `PHASE_APPROVED` and its `depends`
   done. What Codex approved is **sealed** (`progress/plan_roadmap.sha256`,
   `progress/plan_phase_<NN>.sha256`): editing it, except `status`, fails
   `make check` until the gate approves the change.
1. **No code before the plan gate.** Claude does not write to `src/` without
   `progress/plan_review_<N.M.K>.md` whose `**Verdict:**` line is exactly
   `PLAN_APPROVED`. A review that merely mentions the word does not count.
2. **Micro-tasks.** A write to `src/` (or `include/` for C headers, or the dirs
   in `harness.toml`, see [configuration](configuration.md)) must target
   a file declared in the subtask's `files:` (1-3 files; none for a test-only subtask). Paths are resolved
   (symlinks, `..`, `./`) before matching. Anything else is blocked until the
   plan is updated and re-approved.
3. **The oracle is read-only.** Claude never writes to `tests/acceptance/` or
   to the Codex-owned verdicts and seals in `progress/`.
4. **Claude never commits.** The Bash guard parses the command (git global
   options, wrappers such as `env`/`command`, `bash -c`, `eval`, git aliases);
   it does not match substrings (coverage and limits: "Commits and publication"
   below). See `HARNESS_ALLOW_COMMIT` in
   [configuration](configuration.md) for the escape valve.
5. **No `done` without proof.** `progress/review_<N.M.K>.md` = `APPROVED`, a
   complete `docs/reference/<N.M.K>-<slug>.md` (`doc_gate`) and `make check` green.
6. **No agent attribution in commits.** Codex writes the close message;
   `review_with_codex.sh` commits it only after `make check` is green, and
   refuses a message with attribution or without `[N.M.K]`.

### Two layers of enforcement

| Layer | What | Limits |
|-------|------|--------|
| **Per call** (`PreToolUse`) | `guard_write.sh` covers `Edit/Write/MultiEdit/NotebookEdit`; `guard_bash.sh` blocks shell writes to protected paths (redirections, `tee`, `sed -i`, `cp/mv/rm`, `find -delete`, `git checkout/restore/clean/apply`, `patch`, interpreters writing files) | The Bash guard is a best-effort parser: an arbitrary program can always write a file in a way no parser sees. |
| **Outcome** (`make check` → `_guard.py integrity`, also run by the Stop hook) | Every `src/` change vs `HEAD` must be in the declared `files:` of the in_progress subtask, or of the subtask being closed (done in the tree, not yet in `HEAD`, code `APPROVED`); sealed acceptance tests must be byte-identical; sealed plan files must be unchanged | Needs git history (skipped with a warning before the first commit). |

### Commits and publication: what the guard covers and where it stops

The harness makes the single commit of a subtask (the close) and pushes the
branch / opens the PR (`review_with_codex.sh pr`); only the human merges.

| Operation in a Claude Bash call | Decision |
|---|---|
| `git commit`, also behind wrappers and their options (`env`, `command -p`, `exec -a`, `nice -n`, `timeout -k … DURATION`, `stdbuf -o0`, `sudo -u`, `time -p`, `setsid`, `ionice`, `flock FILE CMD` / `flock -c`, `script -c`, `uv run`), `bash -lc` / `sh -c` / `eval`, `xargs git …`, `find -exec git …`, a project shell script run by the call (`bash f.sh`, `./f.sh`, `source f.sh`), and git aliases from the repo config, `-c alias.X=…`, `--config-env`, `GIT_CONFIG_PARAMETERS` / `GIT_CONFIG_COUNT`, or a `git config alias.X …` earlier on the same line | **BLOCK** (escape valve: `HARNESS_ALLOW_COMMIT=1` in the environment Claude Code starts with) |
| An alias whose value the guard cannot know (dynamic value, `include.path`, a config file written earlier on the line) | **BLOCK**, fail closed |
| `git commit-tree`, `update-ref`, `revert`, `cherry-pick`, `pull`, `merge`, `rebase` (not with `--abort`/`--quit`/`--no-commit`) | **WARN** (plan 0.5): allowed, the hook tells Claude and the user |
| `git push` (not `--dry-run`), `gh pr create`, `gh pr merge` | **WARN** (plan 0.5) |
| `git am`, `git apply`, `patch`, the sealers | **BLOCK** (unchanged); also in the `permissions.deny` list of `settings.json` |

`settings.json` allows without a prompt only the harness `make` targets and
`uv run pytest|ruff|mypy`; any other `make …` (`make -f other.mk`) or
`uv run <program>` asks first. The deny list holds only what the guard always
blocks with no valve, so it never removes a legitimate path.

**Manual commits** (issue #61, item 5). A session started with
`HARNESS_ALLOW_COMMIT=1` may commit only a tree the harness has seen green: the
guard compares the green record (`.git/harness-check.ok`, written only by
`harness/run_check.sh --record` after a clean green check of an unchanged tree)
with the fingerprint of the tree at the moment of the call — the same check as the
PR barrier of #55, index flags included. A missing, stale or unverifiable record is
a **WARN** for now (the commit goes ahead) and becomes a **BLOCK** in the WARN→FAIL
calendar. `HARNESS_ALLOW_COMMIT=force` is the human valve: it skips the record check
and appends one line (UTC time, `HEAD`, fingerprint; never the command) to
`.git/harness-commit-force.log`, which Claude's tools cannot write. Limits: the
fingerprint is taken before the command runs, so a `git add` in a *separate* call
before the commit moves the status and makes the record stale (stage and commit in
one call, or re-run the check after staging); an edit made earlier on the same line
(`echo x > f && git commit -a`) is not seen; a `git -C <other>` commit is compared with
the project's own tree.

**Outcome check.** `make check` (`_guard.py integrity`) lists the commits on the
branch past its base (`origin/HEAD`, else `main`) that the close did not make —
a close commit has a subject ending in `[<leaf>]` and is the commit that marks
that leaf `done` in `feature_list.json` — and reports each one as a WARN; a
merge that only brings the base in is not reported. It never changes the exit
code yet (plan 0.5).

**Residual limits** (documented, not covered): any program the guard does not
parse can run git (`python -c "subprocess.run(['git','commit'])"`, a script in
another language, a `make` recipe, a git hook or `core.hooksPath`); a shell
script outside the project; wrappers not listed above; `gh api` calls; a forged
close (a `[<leaf>]` subject on the commit that marks the leaf done) is
indistinguishable from the real one; commits on the base branch itself are
seen only when `origin/<base>` exists. Interpreters and shell-in-shell variants
beyond the listed wrappers belong to I3c.

**Fail-closed side** (a block where git would not commit): a project script is
read whole, so a `git commit` in a branch that never runs (`if false; then …`,
an uncalled function) blocks it, as it already does on the command line; a
non-builtin git subcommand blocks when the config git would read is unknown
(a `cd`/`env -C`/`sudo -D` to an unresolved or wrapped directory, a dynamic
`-c` value, `include.path`, a `source`d file, a git config file written earlier
on the line); a same-line `git config --global alias.X …` counts even if a
local alias of the same name would win.

### Working-tree fingerprint

`_guard.py fingerprint` is the key of the green record: the Stop hook, the PR
barrier, the gates' record reuse and the manual-commit check above compare it with
`.git/harness-check.ok`. It hashes `HEAD`, `git status`, the diff against `HEAD`, the
contents of untracked (not ignored) files, the toolkit behind the `harness` and
`.claude/settings.json` links, and (issue #61, item 4) a fixed list of files that
drive the check, by content, whether git tracks, ignores or never sees them:
`Makefile`, `GNUmakefile`, `makefile`, `harness.toml`, `feature_list.json`, the whole
`docs/plan/` tree, `pyproject.toml`, `setup.cfg`, `tox.ini`, `pytest.ini` and the root
`conftest.py`. An ignored file outside that list does not count. Anything it cannot
read (a dangling link, an untraversable directory, an unreadable file) gives no
fingerprint, so nothing is green. Files under `.git/` are not part of it (the record
itself, the attempt ledger, the force log, the close message the harness sets aside
as `.git/harness-close-<id>.msg`) unless a listed input is a link into `.git/`.
Limits: every file under `docs/plan/` counts, ignored ones included, so a tool that
writes there during the check (a cache, a coverage file) keeps the record from being
written; inputs are read whole into memory.
When the list was added every existing record stopped matching once; the next gate,
close or `pr` (or `harness/run_check.sh --record`) writes a fresh one.

The attempt ledger of `harness/resume` (`.git/harness-gate-runs/attempts_*.json`) is
written only by the harness steps: `_resume.py begin|end` is a sealer for the Bash
guard (`budget` and the read-only next action stay open), so Claude cannot reset an
attempt budget.

The outcome layer is what makes the rules hold regardless of *how* a file was
written. The close window exists because the documenter marks the subtask
`done` and the harness runs `make check` before the commit; once that commit lands, the
subtask is `done` in `HEAD` and its files are closed again.

Clean code (bounded function size, complexity and arguments) is enforced by
the ruff caps (C90 + PLR09xx) shipped in the canonical `pyproject.toml`
(`skills/py-style/assets/pyproject.toml`), so a violation fails `make verify`
before Codex can approve.

## Language variants

The orchestration core (agents, Codex gates, hooks, plan model, `sync_plan`,
`gate`, `doc_gate`) is language-agnostic. Only the toolchain and the template
set differ:

| Language | Templates | Scaffold | Toolchain behind `make verify` |
|----------|-----------|----------|--------------------------------|
| **Python** (default) | `templates/` | `lib/scaffold_python.sh` | ruff + strict mypy + pytest |
| **C** | `templates-c/` | `lib/scaffold_c.sh` | `gcc/clang -Wall -Wextra -Werror -pedantic` + an `assert.h` test runner; `clang-format`/`cppcheck`/`clang-tidy` when installed |

C projects use `include/<name>/` (public headers) + `src/` (core, adapters,
interfaces). The "type" gate is a strict warning-clean compile; clean code is
enforced by `clang-tidy` when present and always by the Codex review.
Acceptance tests are `tests/acceptance/test_<N.M.K>.c`. `make env-check`
compiles and runs `harness/probes/smoke.c` with the project's strict flags in a
temp dir, without writing to the project.

## On-disk state contract

```
docs/stack.md                      # the stack: each decision and why (claude-planner, versioned)
progress/stack_review.md           # STACK_APPROVED | CHANGES_REQUESTED (Codex)
progress/stack.sha256              # seal of the approved docs/stack.md
docs/plan/PLAN.md                  # vision… + generated index (claude-planner / make plan)
docs/plan/phase-NN-<slug>.md       # one phase: title, goal, tasks (claude-planner)
docs/plan/phase-NN-<slug>/<N.M.K>-<slug>.md  # subtask spec + status (source of truth)
progress/roadmap_review.md         # ROADMAP_APPROVED | CHANGES_REQUESTED (Codex)
progress/plan_roadmap.sha256       # seal of the approved roadmap
progress/phase_review_<NN>.md      # PHASE_APPROVED | CHANGES_REQUESTED (Codex)
progress/plan_phase_<NN>.sha256    # seal of the approved phase breakdown
progress/current.md                # live session, gate checklist, blockers
progress/plan_review_<N.M.K>.md    # PLAN_APPROVED | CHANGES_REQUESTED (Codex)
tests/acceptance/test_<N.M.K>.py   # independent oracle (Codex, read-only for Claude)
progress/acceptance_<N.M.K>.sha256 # seal of the oracle, verified by make check
progress/impl_<N.M.K>.md           # implementer report (Claude)
progress/review_<N.M.K>.md         # APPROVED | CHANGES_REQUESTED (Codex)
docs/reference/<N.M.K>-<slug>.md   # output documentation (Codex), same name as the spec
progress/history.md                # append-only log (Codex, at close)

# issues lane (every <N.M.K> file above also exists for an ISS-<n>.<k> subtask)
docs/plan/issues/ISS-<n>-<slug>.md            # issue header (make issue-start)
docs/plan/issues/ISS-<n>-<slug>/ISS-<n>.<k>-<slug>.md  # issue subtask spec + status
progress/issue_review_ISS-<n>.md   # ISSUE_APPROVED | CHANGES_REQUESTED (Codex)
progress/plan_issue_ISS-<n>.sha256 # seal of the approved issue breakdown
progress/issue_migrations_ISS-<n>.json  # migrates: lists frozen at the issue gate
progress/oracle_migrations/<leaf>.json  # complete record of one oracle migration
progress/issue_draft.md            # draft of a new issue (leader, make issue-new)
progress/issue_draft_review.md     # DRAFT_APPROVED | CHANGES_REQUESTED (Codex)
progress/issue_draft.sha256        # seal of the approved draft (published byte for byte)
progress/pr_ISS-<n>.md             # issue PR narrative (Codex, at the last close)
$(git rev-parse --git-path harness-claim-ISS-<n>)  # local claim token (per working copy)
```

The plan seals hash `PLAN.md` without its generated index and every spec
without its `- status:` line, so `sha256sum -c` on `plan_roadmap.sha256` or
`plan_phase_<NN>.sha256` reports a mismatch: `make check` is their verifier.
Acceptance seals are plain hashes (`sha256sum -c progress/acceptance_<N.M.K>.sha256`
works).
