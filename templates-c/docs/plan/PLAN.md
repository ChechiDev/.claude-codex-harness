## How this folder works

```
docs/plan/
  PLAN.md                                 this file (vision… + generated index)
  phase-NN-<slug>.md                      one per phase: title, goal, its tasks N.M
  phase-NN-<slug>/<N.M.K>-<slug>.md       one spec per subtask (micro-task)
  issues/ISS-<n>-<slug>.md                issues lane: one header per GitHub issue (make issue-start)
  issues/ISS-<n>-<slug>/ISS-<n>.<k>-<slug>.md   one spec per issue subtask (outside every phase)
```

GitHub issues are planned under `docs/plan/issues/`, apart from the phases and
their progression, with their own gate (`ISSUE_APPROVED`); see `harness/WORKFLOW.md`.

- **Every phase exists from the start** with its title and goal, so the whole
  scope is visible and reviewed (roadmap gate).
- **One phase at a time**: phase N+1 gets its tasks and specs only when phase N
  is done (`make check` enforces it).
- **Status lives only in the subtask specs.** Task / phase status,
  `feature_list.json` and the index below are derived by `make plan`.
- Approved plans are **sealed**: editing what Codex approved (except `status`)
  fails `make check` until the gate approves the change.
- `make status` shows the whole plan, every gate verdict and the next step.

Ids: phase `NN` · task `N.M` · subtask `N.M.K`. They are used everywhere else
(`feature_list.json`, `progress/`, `docs/reference/<N.M.K>-<slug>.md`, commit
footer `Plan: docs/plan/phase-NN-<slug>/<N.M.K>-<slug>.md`).

### Subtask spec — `docs/plan/phase-01-email/1.1.1-split-address.md`

```markdown
# 1.1.1 Split address
- status: pending
- layer: core
- depends: none
- risk: low
- surfaces: none
- files:
  - include/<name>/address.h           # crea: public API
  - src/core/address.c                 # crea: implementation
- changelog: added
- incompatible: no
- acceptance:
  - AC1 | returns ERR_NO_AT for an address without '@' | tests/acceptance/test_1.1.1.c
  - AC2 | splits "a@b.c" into "a" and "b.c" | tests/acceptance/test_1.1.1.c

## Description
Pure function that splits an address at its single '@'…
```

- `status` ∈ `pending | in_progress | done | blocked | baseline` (`baseline`: already built before the harness; only the phase gate reviews it).
- `layer` ∈ `core | adapters | interfaces` (adapt to your project).
- `depends`: `none` or subtask ids (`1.1.1, 1.2.3`) that must be `done` first.
- `files:` the **1-3 production files under `src/` or `include/`** it
  creates/modifies (the harness blocks writes outside them), or an empty `files:`
  only for a spec declaring `Test-only verification (no production behaviour change)`
  that changes no production file.
  Unit tests (`tests/unit/`) are not declared.
- `acceptance:` observable criteria, one test each; Codex writes those tests.
- `changelog:` ∈ `added | changed | fixed | removed | security` (comma-separated)
  or `none: <why>`, and `incompatible:` ∈ `no | yes: <what breaks for users>`: what
  the subtask changes for the project's users (`CHANGELOG.md`). Required (the task
  and issue gates check it) once the changelog is activated; `baseline` specs skip it.
- `risk:` (optional) ∈ `low | medium | high` and `surfaces:` (optional) the
  `harness.toml` `[review.surfaces.<name>]` names it touches (built in:
  `security`, `data`, `migrations`), or `none`. They raise the Codex effort and
  add checklists to its plan and code gates; `risk: high` also launches its
  parallel session with `[sessions]` `high_risk_model` / `high_risk_effort`.
  A `files:` entry matching `high_risk_paths` or a surface's `paths` raises the
  rating whatever the spec says, and lowering a sealed rating fails `make check`.
